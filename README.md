# Helpdesk Bottleneck Analyzer

Анализ журнала обращений службы поддержки (event log) для поиска **операционных ограничений (bottleneck'ов)** в процессе, вдохновлён идеями Теории ограничений (TOC).

## Зачем

Стандартная метрика "долго между двумя статусами" сама по себе ничего не говорит о причине задержки: переход может быть медленным потому что это реальное узкое место процесса, либо потому что это формальное ожидание после того, как решение по обращению уже фактически принято (например, финальное закрытие тикета). Проект пытается автоматически отделить одно от другого и подсветить кандидатов, которые стоит разобрать вручную.

## Данные

Используется публичный обезличенный event-log обращений в техподдержку (открытый датасет одной итальянской ИТ-компании, распространяется под открытой лицензией для задач process mining). Лежит в `data/raw/helpdesk.zip`.

**Известное ограничение датасета:** в логе нет разделения времени на "ожидание" и "выполнение" внутри статуса — это не позволяет посчитать чистое время обработки отдельно от времени простоя. Анализ ниже частично компенсирует это через поиск длинного хвоста задержек и проверку финальной позиции перехода, но точную декомпозицию "ожидание vs выполнение" по этим данным получить нельзя.

## Как это устроено

```
data/raw/helpdesk.zip
        │  load_event_log()
        ▼
   сырой DataFrame
        │  normalize_event_log()      — приведение колонок к единому виду
        │  validate_event_log()       — проверка обязательных полей, дублей
        ▼
  нормализованный event log
        │  build_transitions()        — строим переходы between activity
        │  calculate_transition_metrics()  — частота и задержки по переходам
        │  add_transition_categories()
        │  get_operational_bottleneck_candidates()
        │  add_bottleneck_score()     — скоринг: медианная задержка × log(частота)
        ▼
  ранжированный список кандидатов в ограничения
        │  analyze_bottleneck_candidate()
        ▼
  подробный разбор конкретного перехода:
   - формальное закрытие или реальный затор?
   - есть ли длинный хвост редких, но очень долгих случаев?
   - что обычно было до и после перехода
```

Дополнительно `calculate_path_metrics()` считает метрики по целым вариантам пути кейса (не только по отдельным переходам).

## Как запустить

```bash
pip install -r requirements.txt
python inspect_dataset.py
```

Скрипт прогонит весь пайплайн на демо-датасете и выведет в консоль топ кандидатов в ограничения и подробный разбор одного из переходов.

Также есть минимальный каркас на FastAPI (`app/main.py`) для дальнейшего оборачивания пайплайна в API:

```bash
uvicorn app.main:app --reload
```
